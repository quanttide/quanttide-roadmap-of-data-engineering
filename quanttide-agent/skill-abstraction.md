# Skill 的层次化抽象与验证

**来源**：2026-10-09 对话整理（原 skill.md 与 skill_test.md 合并，对话原文见 git 历史）  
**状态**：方法论素材。能否进本仓正文按 CONTRIBUTING 落笔纪律另行确认。

## 问题定义

自动生成的 Skill 呈现三类症状：碎片化、单份超长、与人工 Skill 明显相似却无法被相似度计算捕捉。三者指向同一个结构缺陷：Skill 空间缺少「压缩-抽象」层次，所有程序性知识塌缩在最细粒度上。

超长 Skill 的信息论解释：一份平铺所有变体的 Skill，其信息量等于「意图」加上「变体的约束与步骤」的全量展开，没有做条件编码。正确的表示是一个抽象 Skill 描述公共意图与公共步骤，每个变体只保留差异参数——信息量从全量平铺降为「公共部分加 N 份差异参数」。

## 数学建模

每个 Skill 是一个三元组：意图（它在做什么，抽象层级最高）、约束（环境、工具、前置条件）、步骤序列（具体操作，抽象层级最低）。

整理目标：在 Skill 集合上找到一棵层次化聚类树——叶子节点是当前最细粒度的 Skill，内部节点是抽象后的 Skill（去掉约束差异，保留公共步骤），使用者可在任意层级切一刀决定粒度。

抽象的优劣用最小描述长度（MDL）度量：总信息量 = 描述抽象结构本身的成本 + 给定结构后描述每个具体 Skill 所需的残差信息。最好的抽象是使总描述长度最小的那个。

判断两个 Skill 是否该合并，不能在文本层面进行：同一意图可以用完全不同的措辞，同一动作在不同上下文形态各异。可行路径有二：

1. 三层表示：分别提取意图、约束、步骤的语义表示后加权组合，意图权重最大、动作权重最小。两个 Skill 动作完全不同（一个用容器、一个用集群）但意图相同（部署服务）时，靠意图层拉近距离。
2. 结构比较：把 Skill 编译成动作依赖图，比较骨架同构性。骨架同构、仅节点命令不同的两个 Skill，是同一抽象意图的不同实例。

合并判据：意图相似则可合并；约束不同则合并为参数化变体而非删除；动作重叠则提取公共步骤。

## 验证方法

无监督抽象没有 ground truth，验证思路是以人的判断力为黄金标准，分层建立信心：

- 抽样人工对齐：随机抽取若干对 Skill，人工判断该不该合并，与程序结果比对一致率。一致率高可信任批量结果；中等说明阈值或权重待调；过低说明表示层有问题。不一致的配对逐条归因，比任何指标都有信息量。
- 稳定性测试：多组参数下重复运行，比较聚类结果的一致性（如调整兰德指数）。稳定性差说明表示层信号弱——问题在表示，不在聚类算法。
- 消融测试：逐个关闭各表示层，与人工标注比对。哪一层被移除后结果显著变差，哪一层就真正起作用；若纯文本基线与完整模型相当，结构化提取未产生价值。
- 反向生成测试：从抽象 Skill 加变体参数还原原始 Skill，比较还原相似度。还原无损说明抽象抓住了本质；还原失败说明过度压缩，或合并了不该合并的东西。

分层信心的检查顺序：表示层（近邻抽样肉眼验证）→ 聚类层（逐簇判断该不该在一起）→ 抽象层（抽象描述是否准确）→ 合并层（还原测试）。

## 实操切口

不从最大的 Skill 开始。先取一小组最熟悉的 Skill，人工写的与自动生成的各半，人工标注哪些该合并，作为开发集；程序与标注的差异是调参依据；满意后再放大到全量。
